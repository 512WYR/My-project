## 分工建议

以下是可拆分的任务方向，尚未指定负责人，也不表示已经批准进入下一阶段。

| 方向 | 建议范围 | 协作边界 |
| --- | --- | --- |
| 第一阶段问题修复 | 根据实际测试修复战斗逻辑、概率、状态与反馈 | 修改Core时同步检查现有测试的规则依据 |
| 第一阶段界面与美术 | 中文布局、角色表现、技能反馈、按钮交互 | 保持规则在Core层，素材与界面不改变概率规则 |
| 第二阶段地图与事件 | 路线生成、节点处理、商人、营地与工坊 | 读取玩家理智；已展示内容固定；与战斗通过明确结果接口交接 |
| 第二阶段身体系统 | 四肢损伤、断肢、技能限制、义肢安装 | 保留基本操作；修复机会需要与地图模块共同设计 |
| 第三阶段存档与图鉴 | 冒险保存、随机状态恢复、跨局图鉴 | 先明确完整数据结构与保存时机，不能丢失反馈结算标记 |
| 验证与打包 | 规则与场景测试、运行验收、显示检查、构建 | 由负责人组织；记录实际结果和复现步骤 |

## 提交约定

- 从负责人确认的基础版本建立各自分支，每个修改围绕一项任务提交，合入前说明改动、验证情况与限制。
- Unity资源必须连同对应`.meta`提交，已有资源尽量移动而非删除重建，避免引用失效。
- 上传Unity项目根目录，包含`Assets`、`Packages`、`ProjectSettings`和`Docs`；不要上传`Library`、`Temp`、`Logs`或验证副本。根目录`.gitignore`已有相关排除规则。
- 提前约定共享文件的编辑者，尤其是场景、`GameCatalog.asset`、战斗核心与界面脚本，减少同时修改冲突。
- 新增玩法随机判定使用统一概率接口和冒险随机序列，不混用Unity随机数。无效操作不能消耗行动、次数或随机序列。
- 策划更改先由负责人确认，再同步更新策划与实施计划。进度文档要区分“已编写”“已运行验证”和“已验收”。

负责人验收前，第一阶段仍为当前实施阶段。助手负责代码与修复，运行、自测、打包与验收由负责人处理。
