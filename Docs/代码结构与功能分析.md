# StageOne 代码结构与功能分析

> 面向：接手这个 Unity 工程（`Ruin` / 《界限之间》第一阶段原型）的开发者。
> 目的：说清每个文件负责什么、规则住在哪里、数据怎么流动，以及改动时必须守住的契约。
> 对应版本：`STAGE 01 / 0.4`（已去掉职业系统），代码总量约 6150 行。

---

## 1. 一句话概括

这是一个 **纯 C# 规则内核 + Unity 表现层** 的 Roguelike 原型：玩家带着 4 名队员沿一条三层路线前进，
经历战斗、事件、祭坛、补给站与首领；核心资源是**玩家理智**，它同时决定战斗中的技能形态概率
和路线上的候选数量与房间类型。

工程被刻意切成两半：

- **`Ruin.Core`（规则层）**：不引用 `UnityEngine`，纯 C#，可独立编译、可单元测试。
- **`Ruin.Runtime`（表现层）**：MonoBehaviour、UGUI、ScriptableObject 资产。

这条分界线是整个工程最重要的架构约束，改动时不要打破它。

## 3. Core 层：规则内核

### 3.1 [Models.cs](Assets/StageOne/Core/Models.cs) — 世界模型与枚举

**职责**：定义整个游戏的数据形状，不含任何逻辑分支。

- **枚举**：`SkillForm`（技术/基础/原始）、
  `SkillEffect`（攻击/治疗/守护/增益）、`TargetSide`（敌方/己方）、`SkillTargeting`（点选/全体）、
  `SkillArea`（单体/相邻/溅射/贯穿/全队）、`AllyBuff`（格挡/反击/追击/防御/精准，flags）、
  `RiderKind` / `RiderArea`、`ActionKind`（**只有技能与换位两种**）、`BattleOutcome`、
  `EnemyPattern`（执斧者/低语者/追猎者）。**`HeroRole` 已随职业系统一起删除**，角色由
  `ActorSpec.Silhouette` 字符串标识（"warrior"/"shield"/"gunner"/"medic"）。
- **静态定义（Spec）**：`SkillSpec`、`ActorSpec`、`CombatRules`。
  Spec 是不可变的"蓝图"，描述角色/技能/规则的原始数值。
- **运行时状态（State）**：`ActorState`（一场战斗中的角色：HP、理智、形态、流血、部位列表……）、
  `RunState`（一整局：玩家理智、随机数、地图、英雄、义肢仓库、战斗计数）。
  `RunState.Create()` 是**唯一**的开局构造入口，负责给每名英雄建部位血量并与角色属性脱钩。
- **结算对象**：`FeedbackEntry` / `BattleSettlement` / `BattleEvent` / `ActionRequest`。

**关键约定**：
- `ActorSpec` 上的战斗属性（命中/暴击/闪避/防御/攻击）是**静态的，永不随理智变化**，
  只有部位损伤会临时削减它们。
- `ActorSpec.Speed` 是基础速度/旧数据回退值；`SpeedMin` / `SpeedMax` 是本回合抽取区间（0 表示不启用区间）。
  每回合开始时引擎把掷值写进 `ActorState.SpeedRoll`；要读**有效速度**（区间掷值 + 断腿系数）必须走
  `BattleEngine.EffectiveSpeed`。`Speed` 被运行时改到区间外时视为固定速度覆盖（测试与调试台依赖这条规则）。

### 3.2 [Probability.cs](Assets/StageOne/Core/Probability.cs) — 理智概率引擎

**职责**：全局唯一的概率模型，战斗与地图共用。

- `SanityProbability.Distribution(sanity, outcomes, strength)`：以 logit 形式
  `log(weight) + log(gate) + strength * affinity * x` 计算分布，其中 `x = (sanity-50)/50`，
  `affinity` 决定该项随理智趋高还是趋低。返回归一化后的概率数组。
- `SanityGate`：**角色专用**的激活闸门。`High` 在理智 ≤70 时为 0，`Low` 在理智 ≥30 时为 0，
  中间连续过渡——这就是"低于 30 才可能原始化、高于 70 才可能出现技术灵感"的实现。
  **地图和事件一律使用 `SanityGate.None`**，保证探索概率连续、无跳变。
- `Check()`：把单个基线概率（如事件选项可见性）转成一次理智加权判定。
- `RunRandom`：xorshift32 的可序列化随机源。**全工程不使用 `UnityEngine.Random`**，
  所有抽取都走它，因此随机序列可保存、可复现、可在测试里逐次核对消耗。

### 3.3 [MapModel.cs](Assets/StageOne/Core/MapModel.cs) — 路线模型

**职责**：路线的数据结构与规则表。

- `NodeType`：9 种房间。**数值已被测试钉死**（`NodeTypeValuesArePinned`），
  商人/营地/工坊已从枚举删除、整体前移。第三阶段接入存档后只能往后追加，不能重排。
- `NodeOddsSpec`：房间类型的权重 + 理智倾向（正=高理智更常见，负=低理智更常见）。
- `NodeState`：一个房间。关键字段 `OptionMask`（选项可见性在**掷出时冻结**）、`OptionChosen`。
- `StepState`：路线上的一个位置。`Candidates` 保存该位置的候选房间；`Shown` 表示已冻结、
  永不重抽；`Fixed` 表示固定房间（开局/补给站/电梯/首领，不抽）。
- `MapState`：整条路线 + 楼层、矿石库存、开局增益、宝箱/补给站状态，以及按进房顺序记录的
  `EventHistory`（事件 ID 列表；池耗尽后允许重复追加，供“最久未见”选择使用）。
- `MapRules`：**规则表**（与 `CombatRules` 同层）。默认值住在 `MapGenerator` 里的常量。
  注意文件里对 Boss 平衡的注释：按当前数值首领战**很可能打不过**，且没有任何测试断言能赢。

### 3.4 [MapGenerator.cs](Assets/StageOne/Core/MapGenerator.cs) — 路线生成

**职责**：路线生成的**唯一**入口。

- 路线 = **固定骨架 + 中间可抽段**：每层首尾是固定房间（第 1 层开局是增益房，第 2/3 层是补给站；
  层末是电梯井，最后一层是首领），中间 `StepsPerFloor` 个位置在**走到跟前时才抽**。
- `Resolve(rules)`：把目录里缺字段的旧资产补成默认值。**每个字段都必须显式拷贝**，
  因为这里构造的是全新的 `MapRules`，漏掉的字段会被静默重置。
- **抽取契约**（测试逐条钉死，改动务必同步）：
  - 固定位置**不消耗任何随机数**。
  - 可抽位置：1 次抽取决定候选数量（`BranchOdds`），每个候选 1 次抽取决定房间类型。
  - 同一位置内房间类型不重复——**事件除外**，两个事件并排被允许。
  - 类型不够填满候选时，掩码退回整张表让类型重复，而不是空表。
- `Advance()`：走到下一个位置。**已 `Shown` 的位置原样返回、不消耗抽取**——这是"重渲染不重抽"的根基。
  调试跳层时，中间被跳过的位置仍**按顺序补齐**，保证随机序列与走完全程一致。
- `TypeOdds` / `BranchOdds` / `ExpectedBranches` 都是**纯函数**（不消耗抽取），供 UI 反复渲染概率面板。

默认权重表（`DefaultOdds`，总和为 1）：

| 房间 | 权重 | 理智倾向 |
|---|---|---|
| 战斗 `Battle` | 0.363138 | 0 |
| 精英战 `EliteBattle` | 0.155586 | −1.0 |
| 祭坛 `Altar` | 0.085 | 0 |
| 事件 `Event` | 0.311276 | +1.0 |
| 宝箱 `Treasure` | 0.085 | 0 |

### 3.5 [NodeContent.cs](Assets/StageOne/Core/NodeContent.cs) — 房间内容

**职责**：非战斗房间的全部内容与规则。三个静态类：

- **`OpeningBuffs`**：开局三选一增益——坚韧（全队最大生命 +8，并**重建部位上限**）、
  锋锐（全队攻击 +2）、清明（全队初始理智 +10）。
  关键：增益只写在 `RunState` 里那份**全新副本的 ActorSpec** 上，绝不回写角色资产。
- **`Exploration`**：共享的探索辅助（治疗量、补给站治疗/静养、宝箱饰品）。
  - 事件与祭坛的十套内容已迁到 [EventScripts.cs](Assets/StageOne/Core/EventScripts.cs)；
    本类不再持有事件池，只保留 `Heal`、`SupplyHealParty`、`SupplyCalm` 等被房间页和事件页共用的计算。
  - 治疗只在活着的队员身上生效，阵亡者不复活。
- **`Encounter`**：战斗缩放与掉落。
  - `Scale()` 为精英/首领**生成全新 ActorSpec**（+生命、×攻击、加"精英·/首领·"前缀），
    绝不污染敌人资产。技能引用**故意共享**（只读，且战斗引擎依赖引用相等）。
  - `SuppliesFor()`：只有**打赢**才给矿石；撤退一无所获。
  - `DropProsthetic()`：精英战唯一掉落义肢的途径，返回的是共享表的**新副本**。

### 3.6 [LimbModel.cs](Assets/StageOne/Core/LimbModel.cs) — 部位数据定义

**职责**：部位系统的数据结构，**只有玩家一方有部位**。

- `LimbPart`：头、躯干、手臂、腿部（左右合并，所以每人恰好 4 个）。
- `LimbCondition`：完好 / 重伤（≤半血）/ 断肢（0 血）。
- `LimbPartRule`：部位最大血量比例 + 重伤/断肢的惩罚比例。
- `ProstheticSpec`：义肢（常规义肢只恢复基础功能，无取舍）。

### 3.7 [LimbSystem.cs](Assets/StageOne/Core/LimbSystem.cs) — 部位系统唯一入口

**职责**：部位血量、衰减、修复、义肢的全部操作与属性换算。

**核心规则**：

- 部位血量是**第二条血条**：只降不升，0 血后保持断肢直到装上义肢。
- 部位系统**只属于英雄**：`BattleEngine` 构造敌人时不创建 `Limbs`，`LimbSystem.Damage()` 还会显式拒绝 `!actor.Player` 的目标。因此即使调试工具给怪物挂上部位，怪物也不会重伤或断肢；Battle Lab 的重建部位入口同样只对英雄开放。
- 调试工具与消耗肢体的饰品使用 `ceil(部位上限 × HitRatio)`，默认 `HitRatio = 0.5`，
  于是对所有角色所有部位都是"**一击重伤、两击断肢**"。
- 敌人每次攻击命中后，再按**实际生命伤害**的 `DamageRatio`（默认 0.5，至少 1）磨损随机一个未断部位；
  该值由 `GameCatalog.LimbDamageRatio` 暴露，`LimbSystem.EffectiveDamageRatio()` 负责缺字段回落。
- 属性映射：头→命中、躯干→防御、手臂→攻击、腿→速度。**装了义肢恒返回中性值 1.0**；
  断肢的惩罚**替换**重伤惩罚，不叠加。
- `Damage()` 返回"这次是否造成断肢"；断肢时义肢**随部位一起损毁**（第二次截肢要再费一件义肢）。
- 只有**重伤**能修复；**断肢**只能装义肢，且该部位必须已经是 0 血。
- 部位磨损不区分怪物类型：legacy 假人与设计怪共用 `BattleEngine.WearLimb`；未命中、闪避、格挡、目标死亡、部位全断与金丝苹果锁定都在抽取前返回。
- `Resolve()` 给缺字段的旧资产兜底默认值（与 `MapRules` / `LimbRules` 同样的思路）。

默认部位规则：

| 部位 | 血量比例 | 重伤惩罚 | 断肢惩罚 |
|---|---|---|---|
| 头 | 0.30 | −10% 命中 | −25% 命中 |
| 躯干 | 0.45 | −20% 防御 | −40% 防御 |
| 手臂 | 0.35 | −20% 攻击 | −45% 攻击 |
| 腿 | 0.35 | −20% 速度 | −45% 速度 |

### 3.8 [BattleEngine.cs](Assets/StageOne/Core/BattleEngine.cs) — 战斗引擎

**职责**：一场战斗的全部状态机。这是 Core 里最复杂的文件。

**回合流程**：
1. 构造时收集存活英雄、重置战斗内效果、实例化敌人，登记本场起始理智快照。
2. `Advance()`：回合结束时进入下一轮；先跑回合开始钩子（Boss 召唤等），再让每个存活单位按
   `ActorSpec.RollSpeed` 抽取本回合速度（固定速度与死亡单位不消耗随机数），最后按
   **有效速度降序 → 玩家优先 → Id 字典序**重建行动队列。取队首后交给当前行动者。
3. 轮到某人时依次处理：流血跳伤 → 打断检查 → **玩家在此时才抽形态**（`FormProbabilities`）→ 交还控制权。
4. 玩家行动通过 `Execute(ActionRequest)`；敌人通过 `ExecuteEnemy()`（由 App 的协程驱动）。

**形态概率**（`FormProbabilities`）：技术形态受 `SanityGate.High` 管制、原始形态受 `SanityGate.Low` 管制、
基础形态永远可选。**形态在角色回合开始时抽定，本回合内不再改变**（即使理智被调试工具改了）。
形态唯一的可观测作用是 `SkillsFor(actor)` 返回哪一份技能列表：常态四技能、技术形态四技能加特殊技能、
原始形态只剩变化后的那一个技能。

**玩家 2 种行动**（`ActionKind`）：技能与换位。防御、稳定心神、直视深渊与撤退已删除；全队阵亡即 `Defeat`。

- `SkillsFor(actor)` / `SkillFor(actor, index)`：按形态取列表与单项。
- `Targets(index)`：只返回**玩家可点的主目标候选**（点选型技能）。范围（相邻/溅射/贯穿/全队）
  不在 UI 层展开，而由结算期的 `BuildArea` 决定，避免界面重复实现范围逻辑。
- `SwapTargets()`：相邻的存活队友。
- `SkillDisabledReason(index)` / `SwapDisabledReason()`：依次检查站位掩码 → 技能次数（`UsesLeft`）
  → 是否有合法目标，返回 `null` 表示可用。
- `Execute(ActionRequest)`：技能分支选主目标（`RandomTarget` 时随机抽一次，不点选）→ `SpendUse` →
  `ResolveSkill`；换位分支与旧版一致。

**技能机制**（对应四份 `*技能记录.md`）：
- `BuildArea` 生成命中集合：`Adjacent`（左右相邻，受 `AreaMax` 限制）、`Splash`（按距离取最近 N 个）、
  `Pierce`（只向后、按 `AreaDecay` 递减）、`Party`/`Targeting.All`（己方全体）。
- `DamageFor` 算伤害：主目标全额倍率，旁支按 `AreaRatio` 或 `AreaDecay`；`IgnoreLimbPenalty`
  临时忽略部位减益，`HpMissingDamageScale` 按已损失生命增伤，`LimbBonusPerStack` 按非完好部位加固定值。
- `ApplyOnHit` 处理命中后效果：失衡（跳过下一次行动 + 位移必中2回合 + 登记下回合免疫；打断计数与必中窗口分开保存）、流血、打断（**仅主目标**）、拖拽。
- `ConsumeBlock` / `TryCounter` / `TryFollowups` / `MoveSelf` / `PullToFront`：格挡免伤、反击、追击、前移与拖拽。
  追击用 `fromFollowup` 保证不连锁；反击造成的伤害同样可以触发追击。
- 回合开始时统一清除 `DefenseBuff` / `AccuracyBuff` / `SelfVulnerable` / `BlockCharges` / `Counter` /
  `Followup`，因此这些增益都恰好持续一个回合。守护（`ProtectorId`）不在此处清除，而是在守护者自己回合开始时解除。

**伤害计算**：
- 技能伤害 = `ceil(基础攻击 × 技能倍率 × 部位攻击系数)`；暴击 ×1.5（向上取整）。
- 受伤 = `ceil(原伤害 × (1 − 有效防御))`，防御姿态再 ×0.5，易伤（`SelfVulnerable`）再 ×(1+该值)，**下限恒为 1**。
- **流血无视防御属性与防御姿态**，但照样受易伤影响。
- 命中 = `角色命中 × 部位命中系数 + (技能命中 − 0.9) + 全队精准增益`，**不随理智变化**。

**死亡门**：玩家 HP 归零不立即死亡，进入"濒死"；濒死状态下再次受伤做一次死亡检定
（`DeathChance`，低理智更容易死）。敌人 HP 归零直接死。英雄死亡**本局不可恢复**。

**敌人 AI**：按模式选目标——执斧者打最前排、低语者打**理智最高**者并扣理智、追猎者打**血量最低**者并施加流血。
`Intent()` 是**纯函数**，可反复渲染攻击预告而不消耗抽取。

**部位伤害**：攻击真正命中并造成实际 HP 伤害后，随机一个未断部位按
`ceil(实际伤害 × DamageRatio)` 磨损，每次命中最多一个部位。未命中、闪避、格挡、目标死亡、
部位全断与金丝苹果锁定**一次抽取都不花**。

**战后结算 `Finish()`**：玩家理智变化 = 存活队员理智净变化的**平均值 × FeedbackFactor(0.5)**，
钳制到 [0,100]。**结算只能发生一次**（`Settlement != null` 时直接返回）。

## 4. Runtime 层：资产与表现

### 4.1 资产定义（[MainGame/Runtime/Data/](Assets/MainGame/Runtime/Data/)）

三个极薄的 `ScriptableObject` 包装，把 Core 的 Spec 暴露到 Inspector：

| 文件 | 包装 | 说明 |
|---|---|---|

### 4.2 [GameCatalog.cs](Assets/MainGame/Runtime/Data/GameCatalog.cs) — 总目录

**职责**：一个 `ScriptableObject` 装下全部内容与调参入口。

- 暴露的英雄/敌人数组，以及所有平衡数值（概率强度、反馈系数、死亡概率、
  暴击倍率、心神步长、地图楼层/步数/权重/缩放，以及**部位血量比例与惩罚**）。
- `Rules()` 组装 `CombatRules`；`LimbRules()` 组装部位规则；`MapRules()` 组装地图规则（**内部走 `Resolve`**）。
- **重要设计说明（代码注释反复强调）**：**房间权重表**和**义肢表**故意留在代码常量里
  （`MapGenerator.DefaultOdds` / `LimbSystem.DefaultProsthetics`），不放资产——
  因为"已存在的 `.asset` 不会自动获得新增的数组字段"，放进资产会静默读到空引用。
  只有"标量旋钮"放在资产里。

### 4.3 [StageOneApp.cs](Assets/MainGame/Runtime/StageOneApp.cs) — 流程控制器

**职责**：整个游戏的**状态机与流程**，预制体页面只负责画它。它没有游戏规则，只有"现在该显示哪一页"。

- **两条互相排斥的主线**：
  - `AwaitingNode == true` → 显示路线/房间页；此时 `Battle` 为 null。
  - `AwaitingNode == false` → 显示战斗页。
  - `RoomView`（Map/Buff/Supply/Event/Elevator/Treasure）决定节点侧显示哪一页。
- **一局的生命周期**：`NewRun()` → `RevealStep()`（`MapGenerator.Advance`）→ 玩家 `SelectNode()`
  → 对应房间/战斗 → `ResolveCurrent()`（标记已走 + `WalkForward()`）→ …… → `FinishRun()`。
- **房间页**：增益房（`ChooseBuff`）、补给站（治疗/静养每座各一次且第二层免费、第三层起各 2 矿石；
  每座第一次修复免费、之后 1 矿石；安装义肢 1 矿石）、
  事件与祭坛（`EventScripts.Roll` 冻结内容并写入 `MapState.EventHistory`、`ChooseEventOption` 结算）、
  电梯井（纯过渡，`AdvanceFloor`）、宝箱房（发放饰品，`EventFlag` 兼作已领取标记）。
- **新 UI 的页面归属**：`ExplorationMapController` 画路线与房间选择；其余 `RoomView`
  （Buff/Supply/Event/Elevator/Treasure）和本局结束页都由 `IndustrialEventPage` 按事件页结构显示，
  内容由 `Ruin.Runtime.RoomPages` 从同一批 `StageOneApp` 命令生成。
- **战斗页**：`SelectSkill(index)` 选技能（或 `SelectSwap()` 换位）→ `SelectActor` 点目标 → `Submit`
  → 协程 `ContinueEnemies` 逐个驱动敌人行动并播放动画。群体/自身技能第一次点击只记录
  `InspectedSkill`、进入 `PendingSkill` 并显示说明，同时高亮其目标侧的全部存活角色；再点击任意高亮目标
  才提交释放，效果作用于整侧，提交的目标 id 由引擎忽略。不可用技能只写 `InspectedSkill`，
  说明区显示原因，但不会进入 `PendingSkill` 的待释放状态。
- **`MapNote` vs `RoomNote`**：`RoomNote` 每次走位都被清空，所以**战斗奖励写在 `MapNote`** 上，
  否则"没人能读到的奖励等于没发"。
- **节点资源清单**：进入节点时 `StageOneApp.BeginNodeGains()` 对矿石与三类库存（饰品/道具/义肢）
  拍快照，页面用 `NodeGains()` 取净增量，只报告正增长。战斗奖励由结算页调用
  `EnsureBattleRewards()` 提前入账（`ContinueBattle()` 复用同一幂等入口，不会重复发放），
  `RoomPageView.Rewards` 再交给 `IndustrialEventPage` 以金色富文本单独列出。
- **调试工具（`#if UNITY_EDITOR || DEVELOPMENT_BUILD`）**：`StageOneApp.DebugConsole.cs` 与
  `IndustrialDebugConsole` 提供 `DebugSetPlayerSanity`、`DebugSetHeroSanity`、`DebugForceRoom`、
  `DebugEnterFloor`、`DebugInjureLimb`、`DebugSeverLimb`、`DebugGrantAllConsumables`、
  `DebugFeedbackExample` 等，全部由屏幕上的「调试台」调用。不再有 F1/F3 快捷键。
- **角色面板命令**：`CharacterPanelCommands.cs` 是 `StageOneApp` 的 partial，承接原
  `StageOneCharacterPanel` 的开关、药剂、饰品与义肢命令；`Assets/CharacterPanelUI` 只绑定这些命令。
- `DefaultSeed = 44972`：固定种子，保证可复现。

## 7. 一局的数据流

```
GameCatalog.asset ──ToSpec()──> ActorSpec[]（全新副本）
        │                              │
        │ Rules()/MapRules()           ▼
        ▼                       RunState.Create()
   CombatRules / MapRules ────────────> RunState（英雄 + 部位 + 随机源 + MapState）
        │
        ▼
  MapGenerator.Advance() ──> StepState（候选房间，走到跟前才抽）
        │
        ▼ 玩家 SelectNode()
  ┌─────────────┬──────────────┬───────────────┐
  │ 战斗/精英/首领│ 事件/祭坛     │ 增益/补给站/电梯/宝箱│
  │ Encounter    │ RollEvent    │ 直接改 RunState  │
  │  .Scale()    │ 冻结 OptionMask│（治疗/修复/增益）│
  │ BattleEngine │ ApplyOption  │                │
  │  → Settlement│              │                │
  └──────┬───────┴──────────────┴───────────────┘
         │ Finish()：玩家理智 = 队均净变化 × 0.5
         ▼
  ResolveCurrent() → WalkForward() → 下一个位置（随机源继续推进）
         │
         ▼ 走到最后一层的首领 → FinishRun(Cleared?)
```

所有随机抽取都来自 `RunState.Random` 这**一个** xorshift32 流；任何地方都不碰 `UnityEngine.Random`。

## 8. 改动时的"地雷"清单

1. **Core 不许 `using UnityEngine`**。`noEngineReferences` 会在编译期拦下，但设计上也要守住。
2. **随机数契约**：改动地图/战斗流程时，务必保证"纯函数"（预览、渲染）**不消耗抽取**。
   测试会逐次核对 `Run.Random.State`。新增一次抽取会让所有确定性测试失效。
3. **不要回写资产**：凡是从目录拿 Spec 的地方都必须走 `ToSpec()` 或 `Encounter.Scale()` 这类**拷贝**路径。
4. **新数组字段要放代码常量，不要只放资产**（`GameCatalog` 注释的核心教训）；标量旋钮才放资产。
5. **`NodeType` 数值已冻结**，第三阶段起只能追加不能重排。
6. **`MapRules` / `LimbRules` 的 `Resolve` 必须逐字段拷贝**，漏一个字段等于把它静默归零。
7. **首领战当前大概率打不过**（`MapRules.BossHealthBonus/BossAttackScale` 的注释明说），
   没有任何测试断言能赢；在声称通过"通关"验收前先在资产里调参。
8. **UI 只来自预制体**：不要在运行时新建页面或 Canvas；新增页面应做成预制体并订阅 `StageOneApp.Changed`。

## 9. 常见修改指南

### 9.0 动手之前：三条前提

**① 先跑一次 `GameMake/Prepare Stage One`。**

磁盘上的 `Assets/StageOne/Resources/StageOne/GameCatalog.asset` **是旧的**：YAML 里只有
`ProbabilityStrength / FeedbackFactor / DeathChance / MindStep` 四个键，地图、事件、肢体、缩放字段**全部缺失**。
缺失的字段回落到 C# 里的初始值（所以暴击仍按 1.5 生效），但**初始值为空的字段（`MapNodeOdds`、`Events`）
会走 `MapGenerator.Resolve` 的兜底**。也就是说：你现在在 Inspector 里**看不到也改不了**房间权重表和事件列表。
跑一次 `Prepare` 会触发 `Migrate()`，把这些字段回填进资产，之后才能在 Inspector 里调。

**② 资产优先，代码兜底。**

| 想改的东西 | 改哪里 |
|---|---|
| 标量旋钮（概率强度、反馈系数、缩放、部位比例……） | **Inspector 里的资产** |
| 数组/表格（房间权重、义肢、事件默认池、三份技能列表） | **代码常量**（Unity 旧资产不会自动获得新增数组字段） |
| 文本、布局、颜色 | 对应预制体（HUD / MapExploration / IndustrialEventPage / CharacterPanel / DebugConsole）与 `RoomPages.cs` |

**③ `Asset<T>()` 永不覆盖已存在的资产。**

[StageOneBuild.cs](Assets/StageOne/Editor/StageOneBuild.cs) 的 `Prepare()` 是**幂等且只增不改**的。
所以你改了 `Character()` / `Skill()` / `Enemy()` 的调用之后，**直接重跑 `Prepare` 不会更新已有资产**。
两条路选一条：
- **推荐**：直接在 Inspector 里改 `.asset`（保留从此处继续编辑的自由）；
- 或者：**删掉对应的 `.asset` 文件**（如 `Characters/warrior.asset`、`Skills/w_cleave.asset`）再跑 `Prepare`，让它重新生成。

> **本次去掉职业系统后必须先删后生成**：旧资产 `Characters/{guard,scout,arbalist,medic}.asset`、旧的
> `Skills/*.asset` 与 `GameCatalog.asset` 会把新角色挡在外面（新奶妈的 id 也是 `medic`，与旧资产撞名）。
> 删除这些资产，再跑一次 `GameMake → Prepare Stage One`，最后打开 `Assets/Scenes/mainScene.unity`。

| 房间类型权重与理智倾向 | `GameCatalog.MapNodeOdds` | ✅ **需先 Prepare 回填** |
| 候选数量（1/2/3）的权重 | `GameCatalog.MapBranchWeights` | ✅ |
| 候选数量对理智的敏感度 | `GameCatalog.MapBranchAffinity`（默认 1.5） | ✅ |
| 探索概率的整体强度 | `GameCatalog.MapProbabilityStrength`（默认 1） | ✅ |
| 层数 / 每层步数 | `GameCatalog.MapFloors` / `MapStepsPerFloor` | ✅ |
| 无资产时的兜底权重表 | [MapGenerator.cs:19-26](Assets/StageOne/Core/MapGenerator.cs#L19-L26) `DefaultOdds` | ❌ |
| 每场战斗/精英/首领的矿石数 | `GameCatalog.SuppliesPerBattle / Elite / Boss` | ✅ |

| 精英/首领的加血与攻击倍率 | `GameCatalog.Elite*` / `Boss*` | ✅ |

**注意**：`MapNodeOdds` 是"权重 + 倾向"的表格。**权重只决定相对比例**（内部会归一化），
**倾向（Affinity）** 才决定这个房间随理智变多还是变少（负=低理智更多，正=高理智更多）。
把某项权重设为 0，它会**保留在表里但永远抽不到**（路线页的概率面板也不显示它）。

**新增或删除房间类型**要同时改这几处（当前 9 种已全部有实现）：
1. [MapModel.cs:10](Assets/StageOne/Core/MapModel.cs#L10) `NodeType` 枚举 —— **只能追加，不能重排**（数值被测试钉死）；
2. [MapGenerator.cs:270](Assets/StageOne/Core/MapGenerator.cs#L270) `Name()` 显示名；
3. [MapGenerator.cs:265](Assets/StageOne/Core/MapGenerator.cs#L265) `IsCombat()`（如果它会进战斗）；
4. [StageOneApp.cs](Assets/MainGame/Runtime/StageOneApp.cs) `SelectNode()` 的 `switch`；
5. [RoomPages.cs](Assets/MainGame/Runtime/RoomPages.cs) 的页面文案与选项，以及
   [RoomPages.cs](Assets/MainGame/Runtime/RoomPages.cs) 中的房间页构造。
漏掉 4/5 不会崩，但会退化成"没有内容，先继续前进"。

**改权重不会破坏随机数契约**（抽取次数不变）；但如果你的改动**新增了一次抽取**，
所有固定种子的确定性测试（`SameSeedProducesTheSameRoute` 等）都会失败——见第 8 节。

### 9.3 改事件与祭坛内容

事件与祭坛内容全部住在 [EventScripts.cs](Assets/StageOne/Core/EventScripts.cs)，不再使用
`EventDefinition` 资产或 `GameCatalog.Events`。

- **目录**：私有 `Catalog` 数组列出十套脚本，每项有 `Id`、`Title`、`Kind`、`Gate` 和 `Healing`。
  `Kind = Event` 进普通事件池，`Kind = Altar` 进祭坛池；`Gate` 决定高/低理智限定。
- **回血标记**：EVT-005 与 EVT-006 必须保持 `Healing = true`。`Pool()` 会在这两套脚本上要求
  `RunState.Battles >= 1`，所以首战前它们不会进入事件池。
- **内容与步骤**：每个事件的选项写在内联的 `EventChoice.Run` 里；节点只保存
  `EventStep`、`EventCount`、`EventLimit`、`EventTarget`、`EventFlag` 等一次性状态。
- **抽取契约**：
  - 进房时由 `EventScripts.Roll` 只抽一次，之后 `Page()` 是纯读取，重渲染不重抽。
  - 祭坛另存两份 `AltarOffer`（资源 → 理智、理智 → 资源），包含随机的资源种类、数量、
    理智结算给玩家还是全队（`PlayerSanity`）与要交割的义体；两项报价都在 `RollAltar` 里抽定，
    `Page()` 只读。队员侧的理智按每人一次结算，生命始终全队，资源一份。
  - 正常抽取优先选 `MapState.EventHistory` 中未出现过的 ID；全部出现过后选最后出现位置最早的
    一条（最久未见）。选中的 ID 追加到历史。
  - `Pick` 在候选子池只有一条时不消耗随机数，否则消耗一次；EVT-001 的挖矿上限另抽一次。
  - 调试强制事件（`forceId`）绕过理智与首战门槛，且不写入历史。
  - EVT-008 的两项祭坛报价在进房时抽定，`Page()` 不再抽取；报价随节点保存，重绘与读档都保持原样。
- **新增事件**：在 `Catalog` 加一项，并在 `Page` 的 `switch` 与 `Choose` 的处理链中接入对应方法；
  若事件会回血，记得加 `Healing = true`。
- **契约**：内容在进房时冻结；隐藏选项点不动、也不改任何状态。祭坛池只有 EVT-008，重复是设施设计。
  祭坛的兑换率是 `EventScripts.AltarSanityPerSupply`（4）、`AltarSanityPerHealth`（1）、
  `AltarSanityPerProsthetic`（16）；改这三个常量即可调整全部报价。

### 9.4 改角色与敌人

**最快的方式：直接在 Inspector 里改 `Characters/*.asset`。** 字段含义：

| 字段 | 说明 |
|---|---|
| `Kind` | `Hero` / `Monster` / `Unset`。只影响 Inspector 显示与 `ToSpec()` 的字段收敛，不进运行时。旧资产先运行 `GameMake/Assign Character Kinds` |
| `Id` / `DisplayName` / `Subtitle` | 内部 id、显示名、副标题 |
| `Silhouette` | 剪影键，玩家填 `warrior` / `shield` / `gunner` / `medic`（**取代旧的 `Role` 职业**）；敌人留空 |
| `MaxHp` / `Speed` | 最大生命 / 基础速度（区间缺失时的固定值） |
| `SpeedMin` / `SpeedMax` | 每回合开始抽取的闭区间。留 0 表示固定速度；正常资产填 `Speed ± 1`。掷值再经部位系数后决定出手顺序 |
| `SanityOffset` | 开局个人理智相对玩家理智的偏移。**职业系统删除后四名角色都是 0**；仅英雄使用，怪物恒为 0 |
| `Attack` / `Accuracy` / `CritChance` / `Dodge` / `Defense` | 战斗属性。**静态，永不随理智变化** |
| `EnemyPattern` | 敌人 AI：`Cleaver`（重劈前排）、`Whisperer`（打最清醒者/扣理智）、`Hunter`（打最虚弱者/流血）。部位磨损不再由它决定 |
| `BasicSkills` | 常态技能列表（常规四技能） |
| `PrimalSkills` | 原始形态（低理智）技能列表。**按文档「失去」措辞只填变化后的那一个技能** |
| `TechnicalSpecial` | 高理智的**那一个**特殊技能。`ToSpec()` 把它并进 `BasicSkills` 生成 `TechnicalSkills`，所以技术形态永远不会丢掉常规技能 |

> 形态 → 列表的选择在 `ActorSpec.SkillsFor(form)`；战斗界面只渲染当前形态的那一份列表。
> **空列表是合法的**（原始形态只有一个技能就是常态），不会崩；但 `BasicSkills` 不能为空，否则常态没有可选项。

**技能字段**（`SkillDefinition` 的 `Spec`）。基础四行是原有字段，后面几组是本次按四份 `*技能记录.md` 新增的机制：

| 字段 | 说明 |
|---|---|
| `Effect` | `Attack` / `Heal` / `Protect` / `Buff`（`Buff` 是不造成伤害的增益技能） |
| `Target` | `Enemy` / `Ally` |
| `Multiplier` | 伤害/治疗 = **基础攻击 × 倍率** |
| `ActorRanks` / `TargetRanks` | 允许施放的站位掩码 / 允许被选中的目标站位掩码 |
| `Uses` | 使用次数限制（0 = 无限）。**按技能 id 计数**，跨形态共享、每次战斗重置 |
| `Bleed` / `BleedTurns` / `BleedChance` | 施加的流血伤害 / 持续次数（默认 2）/ 施加概率（0 = 必定施加） |
| `Interrupt` / `Cleanse` / `Accuracy` | 打断下一次行动 / 清除流血 / 该技能的命中 |
| `Targeting` / `Area` / `AreaMax` / `AreaRatio` / `AreaDecay` | `All` 作用于整方；`Adjacent`（扩散）/ `Splash`（溅射）/ `Pierce`（贯穿）/ `Party`（全队）。`AreaMax` 是副目标上限，`AreaRatio` 是副目标伤害占比，`AreaDecay` 是贯穿每退一格递减的占比 |
| `SelfMove` | 施放时自身位移的格数（−1 = 向敌人前移一位） |
| `PullToFront` / `PullChance` | 命中后把目标拖到对方 1 号位的概率 |
| `Imbalance` | 失衡：跳过目标下一次行动；位移技在施加回合与下一回合（共2回合）对其必中；下回合登记免疫 |
| `IgnoreLimbPenalty` / `HpMissingDamageScale` / `LimbBonusPerStack` / `MaxLimbBonusStacks` / `SelfVulnerable` | 带伤强攻五条：无视断肢攻击惩罚 / 每缺一点血的加伤系数 / 每处伤口的固定加伤与上限 / 施放后自身本回合易伤 |
| `Grant` / `SelfGrant` / `GrantDefense` / `GrantAccuracy` / `FollowupPercent` | 派发给**所有命中目标**的增益 / 只给施放者自己的增益；防御与精准的增幅数值；追击伤害占施放者基础攻击的百分比 |
| `RandomTarget` / `FriendlyFireChance` | 目标改为随机抽取 / 范围里找不到第二名敌人时误伤相邻队友的概率 |
| `Rider`（`Kind` / `Area` / `Ratio` / `SpreadRatio` / `Amount`） | 副效果：`HealFromDamage`（按实际伤害治疗）/ `SanityRestore`（回理智）；`Self` / `SelfAdjacent`（相邻按 `SpreadRatio` 分摊）/ `Chosen`（点选的那一名） |

> **新机制的随机数只在对应开关打开时才掷**：`BleedChance = 0`、`PullChance = 0`、`FriendlyFireChance = 0`、
> 没有 `Rider` 的技能都**不消耗随机序列**。这是与既有抽取次数契约并列的硬约束，改字段时不要顺手加判定。

> **位掩码是最容易搞错的地方**：`ActorRanks` / `TargetRanks` 不是"数量"，是**位的集合**。
> `1 << rank`，rank 0 最靠近敌人。四个英雄是 rank 0/1/2/3。
> 于是 `3`（0b0011）= 前排两格，`12`（0b1100）= 后排两格，`14`（0b1110）= rank 1/2/3，`15`（0b1111）= 全部四格。
> 例：战士的"斩劈"`ActorRanks = 15`、`TargetRanks = 3`（只能打敌人前排两格）。

**加一个新角色**：写 `Character(...)` 调用并挂进 `catalog.Heroes`（默认路径见 9.0 的第 ③ 条）。
注意 **`RunState.Create` 按数组顺序把 `Rank` 设为下标**，所以新角色插在哪个位置会直接影响前后排与换位。
`SilhouetteGraphic` 按 `Silhouette` 字符串分支画剪影（未知字符串落到默认剪影），所以新造型只需加一个分支。

**加一个新敌人**：写 `Enemy(...)` 调用并挂进 `catalog.Enemies`。所有战斗都用这同一组敌人
（精英/首领只是加血加攻 + 加前缀名），所以**新增一个敌人 = 它立刻出现在所有战斗里**。
只想让它出现在某类房间，需要改 `Encounter.Scale` 或 `StageOneApp.StartBattle` 的取敌逻辑。
